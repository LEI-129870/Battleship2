## 1. Objetivo

O objetivo desta tarefa é configurar quality gates no GitHub Actions que falham quando é detetado um problema de qualidade no código, e demonstrar o ciclo **Red → Green**:

1. introduzir uma violação e verificar que o workflow falha (Red);
2. corrigir a violação e verificar que o workflow passa (Green).
   Foram configuradas duas ferramentas:

- **Checkstyle**, para verificar a regra de estilo `ConstantName`;
- **Qodana**, para detetar o code smell de código comentado (*Commented out code*).
## 2. Checkstyle — ConstantName

### Configuração

- Ficheiro de regras: `checkstyle-129849.xml`
- Workflow: `.github/workflows/checkstyle-129849.yml` (*Checkstyle Gate 129849*)
- Regra: `ConstantName`
- Formato exigido: `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*$`
- Severidade: `error`
  A regra `ConstantName` exige que as constantes (campos `static final`) sejam escritas em maiúsculas, com palavras separadas por `_` (por exemplo, `MAX_SHIPS`).

O workflow usa a action `dbelyaev/action-checkstyle` (Checkstyle 12.1.1), analisa o código em `src/main/java` e corre em Pull Requests para o `main`, em pushes para o `main` e manualmente (`workflow_dispatch`). Com `fail_level: error`, qualquer violação faz o workflow falhar.

### Evidências — Red → Green

#### Red — Execução com violação

Foi introduzida uma constante `static final` cujo nome não cumpre o formato exigido. O Checkstyle detetou a violação da regra `ConstantName` e o quality gate falhou.

**Resultado:** FAILURE

**Commit:** `598b058`

#### Green — Execução após correção

O nome da constante foi corrigido para maiúsculas, com `_` entre palavras. O Checkstyle deixou de reportar violações.

## 3. Qodana — Commented Out Code

### Configuração

Foi configurada a inspeção `CommentedOutCode`, que reporta comentários que contêm código Java. Este tipo de código fica rapidamente desatualizado e pode induzir em erro; como o projeto usa controlo de versões, o histórico do Git deve ser usado em vez de manter código comentado.

- Inspeção: `CommentedOutCode`
- Parâmetro: `minLines: 1` (também são detetados comentários de uma só linha)
- Severidade: `WARNING` (reportada pelo Qodana como *High*)
- Quality gate: `failureConditions.severityThresholds.any: 0` — qualquer problema faz o workflow falhar
  O profile usa `baseProfile: empty`, de modo a que apenas esta inspeção esteja ativa.

Foram excluídos da inspeção os ficheiros que já continham código comentado escrito por outros elementos do grupo (`PositionTest.java`, `Fleet.java`, `Position.java` e `Game.java`), para que o quality gate avalie apenas o código desta tarefa.

### Evidências — Red → Green

#### Red — Execução com violação

Foi criada a classe `TestComments.java` com várias linhas de código comentado (por exemplo, `// int x = 5;` e `// System.out.println(x);`).

O Qodana identificou problemas de severidade elevada (*Commented out code*) e o quality gate falhou com a mensagem *"The number of problems exceeds the failThreshold"*.

**Resultado:** FAILURE

[Execução vermelha — Qodana](https://github.com/LEI-129870/Battleship2/actions/runs/42516993712/job/128842084193?pr=54)

**Commit:** `b2d45cb`

#### Green — Execução após correção

O código comentado foi removido do `TestComments.java`. Após a correção, o Qodana não identificou problemas que provocassem a falha do quality gate.

**Resultado:** SUCCESS

[Execução verde — Qodana](https://github.com/LEI-129870/Battleship2/actions/runs/42519886576/job/128850844108?pr=54)

## 4. Reflexão

O Checkstyle e o Qodana permitem detetar automaticamente problemas de qualidade e impedir que sejam integrados no código sem revisão. O Checkstyle é determinístico: a regra `ConstantName` verifica um padrão de nome bem definido e os resultados são claros. O Qodana, no caso do código comentado, baseia-se numa heurística: identifica bem blocos que parecem código, mas pode apanhar comentários legítimos com exemplos de código, e o parâmetro `minLines` influencia o que é reportado.

Durante a configuração do Qodana, o quality gate falhou inicialmente por causa de código comentado que já existia noutros ficheiros do projeto. Foi necessário isolar a análise, o que mostra que um limite de tolerância zero (`any: 0`) deve ser introduzido com cuidado em projetos que já têm dívida técnica. Os resultados das ferramentas devem ser analisados em conjunto com o contexto do código.
